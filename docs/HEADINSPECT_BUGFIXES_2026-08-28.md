# HeadInspect --- журнал исправлений и логика аудита

**Дата:** 28 августа 2026\
**Назначение:** зафиксировать найденные за день проблемы, исправления и
важную логику обработки URL, чтобы при дальнейшей разработке не вернуть
уже устранённые ошибки.

## 1. Утренний инцидент: тяжёлые аудиты и ощущение «подвисшего» backend

Утром проверялась работа backend на реальных сайтах, в том числе на
крупных sitemap.

По логам было видно, что сам API продолжал принимать задания и запускать
их, однако некоторые внешние сайты отвечали очень медленно. Особенно
показателен аудит `yandex.ru`: discovery нашёл 500 страниц в 14 sitemap,
после чего большое количество отдельных страниц упиралось в page timeout
30 секунд.

Аналогичная ситуация наблюдалась при проверке `aforizm.org`: discovery
успешно нашёл 500 страниц, но затем множество страниц получили
`Page audit timed out after 30s`.

Это важно отличать от падения API: медленный или зависающий проверяемый
сайт способен надолго занять обработку аудита, хотя сам контейнер
HeadInspect остаётся жив.

После диагностики проверялись небольшие и средние сайты. Например,
`moskostumer.ru` стабильно проходил 100/100 страниц примерно за 11
секунд. Несколько повторных запусков также успешно завершались. Для
защиты от слишком частых запусков с одного IP работал rate limit и
возвращался HTTP 429.

После стабилизации `headinspect.ru` проходил аудит 6/6 страниц примерно
за 1--1,5 секунды. Контейнер `headinspect-api` оставался в нормальном
состоянии; в одном из контрольных замеров использовалось около 67 MiB
RAM из доступных 448 MiB.

### Вывод

При будущей диагностике необходимо различать:

-   недоступность самого `api.headinspect.ru`;
-   общий timeout всего audit job;
-   timeout отдельной проверяемой страницы;
-   медленный discovery sitemap;
-   очередь аудитов;
-   rate limit HTTP 429.

Большое количество `Page audit timed out after 30s` ещё не означает, что
backend HeadInspect упал.

## 3. Sitemap ошибочно показывал доступные URL как недоступные

### Симптом

В Sitemap страница могла иметь:

-   HTTP 200;
-   рабочий конечный URL;
-   нормально открываться в браузере;

но HeadInspect показывал:

> URL из sitemap недоступен

Причина оказалась не в доступности страницы.

### Причина

Frontend Sitemap использовал общий массив `page.errors`.

В `page.errors` находятся не только сетевые ошибки страницы, но и
результаты других анализаторов. Например, отсутствие `og:title` или
`og:image` могло попасть в общий набор ошибок страницы.

В результате Sitemap воспринимал ошибку Open Graph как доказательство
недоступности URL.

### Исправление

В `site/sitemap.js` Sitemap перестал использовать `page.errors` для
определения доступности.

Теперь логика Sitemap основана на HTTP-состоянии URL:

-   нет HTTP-кода → ошибка доступности;
-   HTTP \>= 400 → ошибка;
-   редирект → предупреждение;
-   успешный конечный ответ → OK.

Ошибки Open Graph, Meta и Schema на статус Sitemap больше не влияют.

## 4. Неверный счётчик Sitemap в общем аудите

После исправления подробного Sitemap-аудита обнаружился второй баг:

-   подробный Sitemap показывал `0 ошибок`;
-   на главной странице общего аудита блок Sitemap продолжал показывать
    `500 ошибок`.

### Причина

В `site/home.js` функция подсчёта Sitemap по-прежнему считала наличие
`page.errors` ошибкой Sitemap.

### Исправление

`moduleTotals()` для Sitemap приведён к той же логике, что и подробный
Sitemap:

-   HTTP-ошибка/отсутствие ответа → error;
-   редирект → warning;
-   доступный URL → OK;
-   ошибки контентных анализаторов игнорируются.

После исправления общий аудит и подробный Sitemap показывают
согласованные результаты.

Коммит:

`a9648c9 Fix sitemap totals in general audit`

## 5. Как трактуется редирект в Sitemap

На `vacuum.msk.ru` найден URL из sitemap:

`/vakuumnaya-upakovka-vakuumnye-upakovschiki`

Он приводит на главную страницу `/`.

В результате HeadInspect показывает:

-   URL из sitemap --- исходный адрес;
-   конечный URL --- главная страница;
-   конечный HTTP-код --- 200;
-   статус --- предупреждение «Редирект на другой URL».

Это корректно.

HTTP 200 относится к **конечному ответу после перехода по редиректу**.
Сам факт того, что URL из sitemap ведёт не на себя, а на другой URL,
остаётся отдельным предупреждением Sitemap.

## 6. Ложные дубли Meta из-за редиректа

Следующая проблема проявилась в Meta.

В результатах одновременно присутствовали две строки `/`. Одна
соответствовала настоящей главной странице, вторая появилась потому, что
другой URL из sitemap перенаправлялся на главную.

Обе записи содержали один и тот же HTML, поэтому backend ошибочно
сообщал:

-   одинаковый `<title>`;
-   одинаковый `meta description`;
-   одинаковый `meta keywords`.

Фактически это не две страницы с дублирующимся контентом, а одна
конечная страница, достигнутая двумя URL.

### Исправление backend

В `backend/app/jobs.py` поиск Meta-дублей теперь пропускает:

-   неудачные проверки (`check_failed`);
-   записи, у которых `requested_url != url`, то есть результат
    относится к редиректному исходному URL.

Редирект при этом не теряется: его продолжает показывать Sitemap.

Коммит:

`a6ab2fa Ignore redirects when detecting meta duplicates`

После backend-изменения VPS был обновлён и контейнер пересобран.
Контрольный healthcheck:

`{"status":"ok","service":"headinspect-api","version":"0.4.0"}`

## 7. Задвоение конечной страницы в OG / Meta / Schema

После исправления Meta-дублей обнаружилась ещё одна связанная проблема.

Backend по-прежнему возвращал результаты для каждого исходного URL
аудита. Поэтому контентные модули могли отображать:

1.  прямую запись конечной страницы `/`;
2.  запись редиректного URL, которая после запроса также имела конечный
    `url = /`.

В интерфейсе получались две одинаковые строки `/`.

### Почему нельзя было просто удалить редиректы из backend

Sitemap обязан сохранить каждый URL из карты сайта. Если URL из sitemap
редиректит, это самостоятельная техническая проблема карты сайта и её
нельзя скрывать.

Поэтому было принято разделение:

-   **Sitemap работает с исходными URL sitemap;**
-   **OG / Meta / Schema работают с уникальными конечными страницами.**

### Исправление frontend

В:

-   `site/app.js` --- Open Graph;
-   `site/meta.js`;
-   `site/schema.js`;
-   `site/home.js`;

добавлена логика `uniqueContentPages()`.

Она группирует успешные результаты по конечному `page.url`.

Если несколько исходных URL пришли к одной конечной странице, контентный
модуль показывает её один раз.

Если одновременно есть:

-   непосредственная запись самой страницы;
-   редиректная запись, ведущая на неё;

предпочтение отдаётся непосредственной записи.

### Важное исключение

`check_failed` и результаты без конечного URL **не склеиваются**.

Для неудачной проверки важен именно исходный URL. Иначе дедупликация
могла бы скрыть реальную сетевую ошибку.

Коммит:

`387725b Deduplicate redirected pages in content audits`

## 8. Итоговая модель на тесте `vacuum.msk.ru`

После исправлений один и тот же audit job даёт разные количества строк в
зависимости от назначения модуля.

### Sitemap

**500 URL**

-   499 OK;
-   1 предупреждение о редиректе;
-   0 ошибок.

Sitemap сохраняет все URL из карты сайта.

### Open Graph

**499 конечных страниц**

Редиректная копия главной не отображается второй раз.

### Meta

**499 конечных страниц**

Главная `/` отображается один раз. Ложные duplicate
title/description/keywords из-за редиректа исчезли.

### Schema

**499 конечных страниц**

Редиректная копия главной также удалена из представления.

### Общий аудит

В заголовке может оставаться:

**500 страниц проверено**

Это количество исходных URL, обработанных audit job.

Внутренние показатели OG / Meta / Schema при этом рассчитываются по
уникальным конечным страницам.

Это не противоречие: это два разных уровня представления результатов.

# 9. Кратко: как backend HeadInspect обрабатывает аудит

Этот раздел фиксирует архитектурную логику, которую важно учитывать при
дальнейших изменениях.

## 9.1. Создание job

Frontend отправляет:

`POST /api/audits`

Backend создаёт `Job` с уникальным `job_id`, сохраняет исходный
`requested_url` и ставит аудит в очередь.

Аудиты ограничиваются `MAX_CONCURRENT_AUDITS` через `asyncio.Semaphore`.
Поэтому новый job при занятой ёмкости может некоторое время находиться в
очереди, не являясь зависшим.

## 9.2. Discovery

После получения слота job переходит в `discovering`.

`discover_audit_urls()`:

1.  нормализует исходный URL;
2.  проверяет `robots.txt`;
3.  читает указанные там `Sitemap:`;
4.  если Sitemap не указан, может искать стандартные адреса;
5.  поддерживает sitemap-index и вложенные sitemap;
6.  собирает URL;
7.  ограничивает аудит значением `MAX_AUDIT_URLS` --- сейчас до 500
    страниц.

В Job сохраняются:

-   `normalized_url`;
-   `robots_url`;
-   `robots_found`;
-   `robots_sitemap_urls`;
-   `sitemap_urls`;
-   `discovered_urls`;
-   признак `limited`.

После discovery job переходит в `running`.

## 9.3. Один обход --- несколько анализаторов

`run_pages(urls, on_result)` выполняет обход найденных страниц.

Важный принцип HeadInspect:

> Страница загружается в рамках общего аудита, а подключённые
> анализаторы используют результаты этого обхода.

Именно поэтому после общего аудита пользователь может переключаться
между Open Graph, Meta, Schema и Sitemap с тем же `job_id` без нового
полного сканирования сайта.

Для каждой обработанной страницы формируется `PageResult`.

## 9.4. Исходный и конечный URL

Для результата важно различать:

-   `requested_url` --- URL, который HeadInspect собирался проверить;
-   `url` --- конечный URL после HTTP-переходов.

Если они различаются, значит исходный URL привёл к другой конечной
странице.

Это различие нельзя убирать из модели: оно необходимо Sitemap и
диагностике редиректов.

## 9.5. PageResult и ошибки анализаторов

Один `PageResult` может содержать результаты нескольких проверок.

Поэтому общий `errors` страницы **не равен** «URL недоступен».

Например, страница может:

-   успешно отвечать HTTP 200;
-   иметь корректный HTML;
-   не иметь `og:title`;
-   не иметь `og:image`.

Для Open Graph это ошибки, но для Sitemap URL остаётся доступным.

Это один из главных выводов сегодняшней отладки:

> Каждый модуль должен интерпретировать PageResult в рамках своей
> задачи, а не считать любой общий `page.errors` ошибкой своего модуля.

## 9.6. Счётчик checked_urls

Каждый результат, переданный через `on_result`, добавляется в
`job.results`, а `job.checked_urls` увеличивается.

Поэтому backend может честно сообщить:

`500/500 pages`

даже если два исходных URL после редиректа привели к одной конечной
странице.

Это количество обработанных исходных URL, а не число уникальных конечных
документов.

## 9.7. Дубли Meta

После завершения обхода backend выполняет
`_apply_meta_duplicate_warnings()`.

Значения:

-   title;
-   description;
-   keywords;

нормализуются (пробелы + casefold) и группируются.

После исправления 28.08.2026 редиректные результаты и `check_failed` не
участвуют в поиске контентных дублей.

Иначе один документ, доступный через прямой URL и редирект, создавал бы
ложный duplicate warning.

## 9.8. Таймауты

Нужно различать два уровня.

**Page timeout** относится к конкретному внешнему URL. Такая страница
может завершиться неудачно, но остальные URL аудита продолжают
обрабатываться.

**AUDIT_TIMEOUT** ограничивает выполнение job целиком. В `jobs.py` весь
`execute_audit()` выполняется через `asyncio.wait_for(...)`. Если общий
лимит превышен, job получает статус `failed`.

## 9.9. Хранение результатов

Результаты сохраняются в `job.results`.

API результатов возвращает:

-   `job_id`;
-   `status`;
-   `checked_urls`;
-   `discovered_urls`;
-   список `results`.

Frontend специализированных модулей получает один и тот же набор
backend-результатов и уже представляет его в соответствии с назначением
модуля.

# 10. Правило, которое нельзя потерять при следующих доработках

Архитектурно теперь существуют две разные сущности:

**URL sitemap / URL задания**

и

**конечная контентная страница**.

Они не всегда соответствуют друг другу один к одному.

Поэтому:

  -----------------------------------------------------------------------
  Модуль                              Что считать отдельной строкой
  ----------------------------------- -----------------------------------
  Sitemap                             каждый исходный URL из sitemap

  Open Graph                          уникальную конечную страницу

  Meta                                уникальную конечную страницу

  Schema                              уникальную конечную страницу

  Будущие контентные анализаторы      по умолчанию уникальную конечную
                                      страницу, если задача модуля не
                                      требует анализа исходного URL
  -----------------------------------------------------------------------

Редирект должен:

-   оставаться видимым в Sitemap;
-   не создавать вторую копию контента в OG / Meta / Schema;
-   не создавать ложные Meta-дубли;
-   не скрывать настоящую неудачную проверку исходного URL.
