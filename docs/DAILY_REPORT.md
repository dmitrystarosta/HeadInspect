# HeadInspect — ежедневный email-отчёт

Простое ежедневное HTML-письмо владельцу сервиса о работе за прошедшие
московские сутки. Это **не** внешний мониторинг: если VPS недоступен, письмо
может не прийти — отдельной системы мониторинга здесь нет.

## Что внутри

- Период отчёта: предыдущие календарные сутки по Europe/Moscow (00:00–24:00 МСК).
- Отправка: ориентировочно 00:05 МСК (host cron, см. ниже).
- Содержимое: состояние backend, число запусков, уникальных сайтов,
  завершённых/неудачных/незавершённых проверок и таблица всех запусков
  (домен, время начала по МСК, тип проверки, статус). Проверки, начатые в
  отчётный день и ещё выполняющиеся на момент отправки, включаются с их
  текущим статусом. При отсутствии проверок письмо всё равно приходит с
  текстом «Сегодня проверок не было. Сервис работает».
- Только компактное HTML-письмо с текстовой альтернативой, без вложений.

## Приватность

Хранятся только служебные метаданные: домен (hostname), тип проверки, статус,
временные метки. **Не** сохраняются IP, email, User-Agent и результаты
аудитов. Журнал не публикуется через API или frontend.

## Хранилище

- SQLite-файл по пути из `HEADINSPECT_STATS_DB` (например
  `/data/headinspect-stats.db`). Таблицы `audit_runs` и `report_sent`.
- Записи старше 30 дней автоматически удаляются при каждом формировании отчёта.
- **Функция выключена, пока `HEADINSPECT_STATS_DB` не задан:** модуль статистики
  работает как no-op, файл не создаётся, поведение сервиса не меняется.
- Запись метаданных идёт в отдельном потоке и обёрнута в try/except — сбой
  статистики никогда не замедляет и не ломает аудит.
- Защита от дублей: дата отмечается отправленной только **после** успешной
  отправки, поэтому при ошибке письмо можно отправить повторно (той же
  командой), а повторный запуск за уже отправленную дату ничего не шлёт.

## Переменные окружения

| Переменная | Назначение | Пример |
|---|---|---|
| `HEADINSPECT_STATS_DB` | Путь к SQLite-файлу статистики (включает функцию) | `/data/headinspect-stats.db` |
| `HEADINSPECT_REPORT_TO` | Получатель письма | `owner@example.ru` |
| `HEADINSPECT_SMTP_HOST` | SMTP-сервер | `smtp.example.ru` |
| `HEADINSPECT_SMTP_PORT` | Порт SMTP (по умолчанию 587) | `587` |
| `HEADINSPECT_SMTP_USER` | Логин SMTP (если нужен) | `headinspect` |
| `HEADINSPECT_SMTP_PASSWORD` | Пароль SMTP — только в `.env`, не в Git | `…` |
| `HEADINSPECT_SMTP_FROM` | Адрес отправителя (по умолчанию = USER) | `headinspect@example.ru` |
| `HEADINSPECT_SMTP_TLS` | `starttls` (по умолч.), `ssl` или `none` | `starttls` |
| `HEADINSPECT_HEALTH_URL` | URL внутренней проверки API для письма (необязательно) | `http://127.0.0.1:8000/health` |

Пароль только через `.env` (файл уже в `.gitignore`); в репозитории секретов нет.

## Развёртывание (действия на сервере)

Изменения инфраструктуры применяются вручную — в архиве `compose.yaml` и
`Dockerfile` намеренно не меняются.

**1. Dockerfile** — создать каталог данных с нужным владельцем (контейнер
работает под non-root `headinspect`). Добавить перед строкой `USER headinspect`:

```dockerfile
RUN mkdir -p /data && chown headinspect:headinspect /data
```

**2. compose.yaml** — примонтировать том и подключить `.env`:

```yaml
services:
  api:
    # ...существующие настройки...
    env_file:
      - .env
    environment:
      HEADINSPECT_ENV: production
      HEADINSPECT_USER_AGENT: "HeadInspectBot/0.4 (+https://headinspect.ru/)"
      HEADINSPECT_STATS_DB: /data/headinspect-stats.db
    volumes:
      - headinspect-stats:/data

volumes:
  headinspect-stats:
```

**3. `.env`** рядом с `compose.yaml` (НЕ коммитить):

```dotenv
HEADINSPECT_REPORT_TO=owner@example.ru
HEADINSPECT_SMTP_HOST=smtp.example.ru
HEADINSPECT_SMTP_PORT=587
HEADINSPECT_SMTP_USER=headinspect
HEADINSPECT_SMTP_PASSWORD=СЕКРЕТ
HEADINSPECT_SMTP_FROM=headinspect@example.ru
HEADINSPECT_SMTP_TLS=starttls
```

**4. Пересобрать и поднять контейнер:**

```bash
cd backend
docker compose build
docker compose up -d
```

**5. Cron на хосте** (00:05 МСК, без постоянно работающих сервисов).

Cron в Ubuntu 24.04 (ISC cron) запускает задания по **системной** временной зоне
и **не поддерживает** строку `CRON_TZ` — на неё полагаться нельзя. Поэтому
расписание задаётся в системной зоне сервера. Определите её:

```bash
timedatectl   # строка "Time zone:"
```

- Сервер в **UTC** (частый вариант на VPS): 00:05 МСК = 21:05 UTC →
  ```cron
  5 21 * * * cd /путь/к/backend && docker compose exec -T api python -m app.daily_report >> /var/log/headinspect-report.log 2>&1
  ```
- Сервер в **Europe/Moscow**: используйте `5 0 * * *` с той же командой.
- Другая зона: пересчитайте 00:05 МСК в неё, либо переведите сервер на нужную
  зону (`sudo timedatectl set-timezone …`).

Точность до минуты некритична: отчёт всегда формируется за **предыдущие**
московские сутки и защищён от повторной отправки, поэтому запуск в любой момент
после полуночи МСК даёт один корректный отчёт за завершившийся день. Время в
самом письме считается по фиксированному смещению UTC+3 и не зависит ни от
`CRON_TZ`, ни от пакета tzdata в образе.

Если на сервере Docker Compose v1 — заменить `docker compose` на `docker-compose`.

## Надёжность

- **Перезапуск Docker.** Задачи живут только в памяти процесса API. При старте
  контейнера все записи, оставшиеся в статусах «в очереди/поиск/выполняется»,
  переводятся в «прервана (перезапуск)», поэтому проверки не зависают в статусе
  «выполняется» навсегда.
- **Без дублей.** Отправка защищена файловой блокировкой (`<db>.lock`, flock):
  два одновременных запуска (двойной тик cron или ручной запуск во время cron)
  не отправят письмо дважды. Блокировка снимается по завершении.
- **Повтор после ошибки.** Дата помечается отправленной только после успешной
  отправки, поэтому при сбое SMTP команду можно запустить повторно — письмо
  уйдёт. Повторный запуск за уже отправленную дату ничего не шлёт.
- **Проверка API в письме — внутренняя** (`GET /health` внутри контейнера), это
  не внешний мониторинг доступности сайта. Переопределяется переменной
  `HEADINSPECT_HEALTH_URL`.

## Проверка вручную

Отправить отчёт немедленно (за прошедшие сутки):

```bash
docker compose exec -T api python -m app.daily_report
```

Если письмо за эту дату уже отправлено — команда ничего не шлёт (защита от
дублей). При ошибке SMTP команда завершится с кодом 1 и залогирует тип ошибки
(без пароля); дата останется неотмеченной, и отправку можно повторить.
